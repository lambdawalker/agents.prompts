# Android Repository Setup wizard: implementation study

This study records the implemented wizard in [`lambdawalker/gradle.android-repo-setup`](https://github.com/lambdawalker/gradle.android-repo-setup), at `main` commit `07bb94b45de909b2570a9c54e18e67bcf34bfe61` (after PR #55). The inspected local source blobs for the CLI, discovery, setup, signing, browser server, and browser assets match that commit. It describes the current Rust CLI and its bundled local browser interface, then separates the reusable design lessons. The screenshots and any static preview should be checked against a running wizard: setup actions depend on Gradle discovery, repository files, vault state, and the selected module.

## Entry and task flow

The terminal entry is the default `android-repo-setup` command or `android-repo-setup setup`; `android-repo-setup setup web [--no-open]` starts the local browser from an Android checkout. Maintained `setup.sh` and `setup.bat` launchers use the checkout's configured CLI pin. The CLI owns the setup logic; the browser serializes the same typed questions and answers over a local HTTP session rather than reimplementing signing or publishing. See [CLI commands](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/main.rs), [setup runner](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/setup.rs), and [browser worker](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/ui/web.rs).

| Phase | Implemented behavior |
| --- | --- |
| Open | A loading state appears while the local session is established. The browser requires a vault passphrase at entry, creating and confirming one in a dialog if no local vault exists. |
| Discover | Gradle evaluates plugin identities, reports Android apps/libraries and JVM libraries, and preserves prior selections by Gradle path. The browser saves the resulting inventory; the separate terminal `select-modules` command changes inclusion. |
| Choose | Each included module has a primary header tab. The active tab filters its action cards and Settings; there is no third, repository-shaped module tab or separate browser module-selection screen. |
| Prepare | Settings gathers applicable fields in one reviewable form. **Setup selected tasks** first brings the user to Settings for review where fields exist; **Run selected tasks** submits the selected module's actions and prepared answers together. |
| Execute | The CLI performs validation, conditional questions, key choices, file previews, and confirmations. Workflow changes are previewed before replacing existing files. Shared credentials or environments can serve several modules, though a selected module scopes the action run. |
| Finish | Progress, process output, colored footer status with icon, module details, and artifacts explain the result. The wizard can run another selection while its local session remains open. |

Gradle discovery uses an injected init script and the Gradle wrapper, not directory-name guesses. A discovery failure leaves previous module selection intact. The browser only permits selected modules and applicable operations, and the Rust runner repeats those checks before executing; client filtering alone is insufficient. See [discovery](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/discovery.rs), [setup runner](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/setup.rs), and [browser renderer](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/ui/web_assets/app.js).

## Module tabs and actions

| Active module kind | Actions shown on its tab | Module output in the right panel |
| --- | --- | --- |
| Android application | APK signing key; Local Gradle signing; APK signing environment; GitHub workflows | Existing APK files under `build/outputs/apk`, or the expected location marked **not built**; relevant workflow files. |
| Android library | Publishing environments; GitHub workflows | Existing AAR files under `build/outputs/aar`, or the expected location; relevant workflows. |
| JVM library | Publishing environments; GitHub workflows | Existing JAR files under `build/libs`, or the expected location; relevant workflows. |

The action descriptions say what will change: signing creates or verifies a keystore and writes the public association file; local signing writes credentials to ignored `local.properties` after confirmation; the GitHub signing environment uploads missing secrets while preserving existing secrets; publishing configures shared credentials/environments and GitHub Pages; workflows generate missing files and review replacements. The **Setup selected tasks** control submits only checked actions on the active module. Module workflow generation takes that module ID; publishing credentials and environments remain repository-shared. See [operation catalog and runner](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/setup.rs) and [artifact catalog](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/ui/web.rs).

## Settings as a complete, deduplicated input surface

The Settings panel shows **Common fields** first when several actions on the active module need the same input, then groups the remaining fields by action. It omits action groups with no advance inputs (for example, GitHub workflows and Local Gradle signing). A dynamic publishing catalog supplies fields from the configured destinations in `.project/setup/repositories.yml`; conditional key selection and final confirmations still occur during execution. Prepared answers are restricted on the server to prompt labels allowed by the chosen actions; vault passphrases and destructive confirmations cannot be staged. See [Settings renderer and draft logic](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/ui/web_assets/app.js) and [prepared-answer validation](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/ui/web.rs).

Fields have semantic keys rather than being duplicated by visual group. A recently entered GitHub token can default the equivalent publishing access token on another module; publishing values share only when environment and variable match. A deliberately cleared input remains blank. Automatically generated app signing credentials remain specific to that app unless explicitly edited; Android application IDs are app-specific. Public signing defaults can include path, alias, and discovered IDs, while saved secrets stay concealed. Green **Saved in vault** ribbons report *presence* only. Password ribbons require a matching keystore path and alias, so a credential from another key is not claimed as reusable. See [shared draft and vault-field logic](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/ui/web_assets/app.js) and [vault metadata API](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/ui/web.rs).

For a *new* APK keystore, the browser supplies an invented three-syllable alias and independent 25-word keystore/key passphrases, with separate regenerate controls. An existing keystore receives no replacement passwords; its original credentials must be verified. The suggested path lies outside the repository and Windows display paths drop the `\\?\` prefix. During the live **Create a Maven Central signing key** form, a fresh 25-word OpenPGP passphrase can be generated or regenerated and its confirmation filled. That OpenPGP form is conditional and is not a static Settings group on every library tab. The generator combines securely selected onset, vowel, and coda fragments with rejection sampling, avoiding a bundled dictionary and modulo bias; the 25 independently generated words provide more than 300 bits of generator entropy. See [signing defaults and generator](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/signing.rs), [OpenPGP endpoint](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/ui/web.rs), and [form controls](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/ui/web_assets/app.js).

## Vault, export, and session boundaries

The wizard runs on loopback with a one-time launch token, then a tab-scoped session and CSRF token. The server checks Host, Origin, session authorization, and action token; it does not serve setup secrets in routine `/api/state`. The initial vault passphrase is retained for use by the active browser worker, so starting selected activities does not ask for it again. After 20 minutes of inactivity, the server locks the session and the browser clears prepared secret drafts and asks again in a dialog. Vault viewing and recreation live in the main menu. See [local server/session](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/ui/web.rs) and [vault dialogs and draft clearing](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/ui/web_assets/app.js).

The main menu also offers two deliberate export paths:

| Export | Contents and gate |
| --- | --- |
| Create Bitwarden secure note | Collects filled/generated fields across module tabs and the current or accepted Maven key form, omitting empty and confirmation fields and deduplicating equivalent values. The user checks the Bitwarden CLI account before creation. Already saved vault secrets are not silently copied to the note; the user must explicitly fill them. |
| Copy setup JSON | Explicitly rechecks the vault passphrase *each time*; merges saved vault values with current form values, lets explicit entries replace matching saved fields, and deduplicates semantic aliases. A second click copies plaintext JSON to the clipboard; closing or locking clears the prepared export. |

The Bitwarden CLI session key may come from the dialog or CLI environment, and the note command sends data over stdin rather than embedding secrets in arguments. A failed or interrupted creation needs an account check before retry to avoid duplicate notes. Generated and entered fields remain in browser memory for export after execution until lock/close. See [export dialogs and deduplication](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/ui/web_assets/app.js) and [Bitwarden/JSON server handlers](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/ui/web.rs).

## Reusable wizard lessons

1. Derive primary tabs from the CLI's discovered domain entities, then filter actions by entity capability. Keep action scope, Settings, details, and artifacts aligned to the active tab and revalidate the choice in the backend.
2. Expose the available operations immediately after discovery. Put meaningful effects, dependencies, and review behavior in each card description rather than an extra explanation button or introductory choice page.
3. Build a full reviewable Settings form from typed prompt fields, deduplicate by semantic key, share only compatible explicit inputs, and omit empty action groups. Leave genuinely conditional prompts and irreversible confirmations in the execution flow.
4. Generate useful secret defaults only for new identities. Keep existing keys and their saved credentials bound to the correct path/alias; offer independent regeneration and an explicit secure export before volatile drafts vanish.
5. Treat vault unlock, inactivity locking, clipboard export, and external password-manager writes as different authorization boundaries. Show saved-field presence without revealing values, and reauthenticate before exporting encrypted vault contents.
6. Show loading during real discovery, keep routine status in a colored footer with an icon, retain detailed errors in Process output, and make artifact panels reflect the active module and whether output was built.

## Evidence and preview limits

The repository includes focused Rust tests for module/action filtering, selected-module answer validation, build-output classification, one-time local authorization, vault creation and idle lock, saved-field privacy, Bitwarden note handling, generation boundaries, and Windows keystore paths in the [browser server tests](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/ui/web.rs), [signing tests](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/signing.rs), [setup tests](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/setup.rs), and [discovery tests](https://github.com/lambdawalker/gradle.android-repo-setup/blob/07bb94b45de909b2570a9c54e18e67bcf34bfe61/cli/src/discovery.rs). This study inspected code and existing tests; it did not run a setup against a live Android checkout or create a vault. A static preview can show the workspace and representative tabs, but cannot prove Gradle discovery, vault unlock, Bitwarden account selection, or actual file mutations.

To capture a faithful preview locally, start `setup.bat setup web --no-open` on Windows (or `sh ./setup.sh setup web --no-open` on Linux/macOS) from a configured Android repository, keep that terminal running, and open its printed one-time loopback link. Unlock or create the vault in the dialog and wait for Gradle discovery. Capture an app tab's **Actions** and **Settings**, then a library tab's corresponding panels and right-side artifacts. For a safe example, use a disposable fixture without real credentials; avoid capturing vault passphrases, generated passwords, Bitwarden sessions, or copied JSON. The authenticated local browser cannot be reached by an external preview service, so no new live screenshot is asserted by this study. The user-provided screenshots during the design review are observations of an earlier local run, not a reproducible preview artifact at this source commit.
